# PLMS Project Tracker

**Target spec:** PLMS Project Blueprint v1.0 (Single Mall MVP) — the PDF supplied 2026-08-19.
**Superseding relationship:** PLMS is the real target. The `parking-system` codebase in this
workspace is treated as an early domain-logic prototype toward it, not a partial PLMS build —
see the stack-compliance note below before reading completion % as progress.

This file was generated by auditing the actual `parking-system` codebase (commit `232e833`)
on 2026-08-19, because no prior tracker existed. It's a baseline, not a record of a real
development history — there was no sprint-by-sprint log to inherit.

---

## ⚠️ Stack-compliance note (read this first)

The blueprint mandates: **Node.js 20 + TypeScript + Express/Fastify + React 18 + PostgreSQL 15
+ Redis + Prisma + Socket.io + Zod**, deployed as a modular monolith with Docker/CI/CD.

The existing `parking-system` codebase is: **Spring Boot 3 (Java 17) + Angular 17 + MySQL**,
no Docker, no CI, no cache layer, no WebSocket layer, no ORM migrations tool.

None of the code below is reusable against the blueprint's stack requirement as written. Every
"completed" item is a *domain-logic prototype* — proof that the entry/exit/booking/pricing
concepts work — not compliant progress. Either the stack mandate needs revisiting, or this is
effectively a rewrite from an architecture perspective.

## Completed (exists today, in `parking-system`, non-compliant stack)

### Auth & RBAC (blueprint Phase 1 analog)
- Register / login / refresh / logout via JWT — but 3 parallel ad-hoc auth mechanisms
  (end user, operator, admin), not blueprint's single `users` table with a 6-value `role` enum
- Role check exists at the route level (Spring Security), not a generic `authorize(roles[])`
  middleware pattern
- No PIN-based login, no force-logout, no login-history UI

### Core parking engine (blueprint Phase 2 analog)
- Single shared `ParkingLot` / `ParkingSlot` model — dashboard, booking, and gate flow all read
  the same slots (this is the one piece of architecture actually done right relative to intent)
- Entry ticket generation (`ParkingTicket`), fee calc on exit, slot release — real logic, works
- No barcode generation, no thermal-printer integration, no QR beyond a JSON string
- No lost-ticket flow, no max-stay enforcement for taxis, no grace-period config

### Gate attendant screen (blueprint Phase 3 analog)
- Entry/exit forms exist (Angular), operator login persists for session
- No shift start/end, no opening/closing cash float, no discrepancy detection, no handover
  notes — **the entire `shifts` concept from the data model does not exist**
- No manual gate override tooling, no dispute flag, no offline fallback

### Floor attendant PWA (blueprint Phase 4)
- **Does not exist.** No PWA, no installable manifest, no offline cache, no floor map,
  no incident reporting, no long-stay highlighting.

### Supervisor dashboard (blueprint Phase 5, supervisor half)
- Operator "live status" page is the closest analog: occupancy by floor/section
- No incident feed (no `incidents` table at all), no alert push, no override approval queue

### Management analytics (blueprint Phase 5, management half)
- Admin dashboard: revenue counter, occupancy, vehicle-type breakdown, 7-day trend chart —
  genuinely working and the strongest overlap with the blueprint of anything in this codebase
- No peak-hour auto-highlight, no long-stay report, no monthly-pass concept, no CSV/PDF export,
  no GST fields, no cash reconciliation (blocked on shifts not existing)

### Admin control panel (blueprint Phase 6)
- Operator CRUD (create/toggle/delete) only
- No general user/role management UI, no system-config UI (pricing/hours/thresholds are
  hardcoded in Java seed classes, not DB-editable — directly contradicts the blueprint's
  explicit "never hardcoded" objective), no monitoring dashboard, no manual
  override/correction tools, no audit log viewer, no backup/restore tooling

### Entrance display (blueprint Phase 7, display half)
- The end-user dashboard shows availability, but it's **authenticated** (blueprint wants an
  unauthenticated public kiosk screen) and polls every 30s with no WebSocket, no LOT FULL state

### Data model compliance
- No `audit_logs` table — blueprint treats this as mandatory and immutable; **zero audit
  trail exists today**
- Money stored as `Double`, not integer paise — the exact floating-point risk the blueprint's
  own risk register calls out (Section 8) is currently live in this codebase
- IDs are auto-increment `Long`, not UUID v4
- No `shifts`, `incidents`, or `pricing_rules` tables; no monthly-pass vehicle type

### Infrastructure (blueprint Phase 0)
- No Docker/Docker Compose, no CI pipeline, no lint/test/build automation, no
  dev/staging/prod environment split, no Sentry, no automated backups
- Local git repo exists (3 commits), which is more version control than 2 of the 3 prior
  prototype folders had — low bar, but true

## Not started (blueprint features with zero equivalent in `parking-system`)

- ANPR/barcode hardware integration, thermal printer integration, barrier gate API integration
- Taxi drop-off flow (flat fee, 30-min max stay), Valet flow, Monthly Pass flow
- Shift management end-to-end (float, reconciliation, discrepancy flagging, handover notes)
- Incident reporting system (floor attendant → supervisor) — no `incidents` table, no UI
- Floor Attendant PWA entirely
- Supervisor alert-push / override-approval workflow
- Admin system-configuration UI (pricing rules, operating hours, overstay threshold, surcharges)
- Monitoring & alerting (system health, gate/printer hardware status, anomaly detection)
- Manual override & correction tools with mandatory-reason audit trail
- Backup & recovery tooling
- Immutable `audit_logs` table and the service-layer enforcement that writes to it
- CSV/PDF report export, GST-compliant transaction export
- Payment gateway (Razorpay/UPI), SMS notifications
- Any automated test suite (unit or integration) — **zero tests exist**
- Docker, CI/CD, staging environment, load testing, security hardening pass
